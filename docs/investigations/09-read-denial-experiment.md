# Investigation 09 — Targeted Firebolt read denial

## Safety and implementation

The 08E entry hook enabled a SafetyHook temporary before its move into the global handle. A callback in that interval could see an empty trampoline and `call()` returns a default value. This experiment constructs the hook with `StartDisabled`, assigns the process-lifetime handle, sets the atomic mode, and only then enables it. SafetyHook `call()` locks its recursive mutex while calling the trampoline; the code does not synchronously wait for a main-thread task. The hook is not deliberately removed while the game is running. Shutdown/unload ordering and a later competing hook still need verification.

The opt-in `UntamedTomes.DenyFirebolt` marker selects entry mode only on 1.7.104. It is mutually exclusive with both observation markers, and retains the existing module, relocation, full-body hash and call-site checks. The decision checks the live callback's reader FormID `00000014`, book `000A26FD`, teaching flag and linked spell `00012FD0`. It does not call `HasSpell`, interrogate UI, wait for a task or mutate inventory. The 08E run observed world callbacks on worker threads. These reads of callback-supplied book/reader data are a narrow tested assumption, not a general guarantee for arbitrary engine pointers or worker-thread operations. Named module checks and current bytes do not cover late detours, unknown plugins or races with another installer; chaining is not supported.

The targeted branch skips the original and returns `false`; diagnostics are wrapped so a C++ logging exception cannot escape or alter that decision. Other inputs invoke the original once; metadata and logging exceptions are contained and cannot cause a second original call, and exit logging cannot change the original result. If the original itself throws a C++ exception, the wrapper returns false and does not retry; effects already performed by that call cannot be undone. C++ catches do not establish safety against invalid pointers or access violations. Synchronous logging and SafetyHook's mutex can block; neither schedules or waits on a main-thread task. This is a disposable-save diagnostic, not a verified production hook.

## Runtime observations, 15 November 2026

The build succeeded and the 1.7.104 startup log reported `tome_read_probe_ready mode=deny_firebolt strategy=entry`. The previous forwarding DLL/PDB, this experiment's build, and same-session native and Papyrus logs are in the native `task08f-preservation` directory. After the initial preservation failure, the denial marker was removed and the previous forwarding DLL/PDB restored; the restored DLL hash was checked against `D116BC7D9BE3FC51551C6C7D8ADAF105CEA115E526527FD73601A7173D6D0063`. Removing a marker alone does not disable an already-running hook.

At 06:47:58, the first reported world READ generated Firebolt inbound and then `tome_read_denied ... original_invoked=0 return=false` on worker thread 26636, without a nearby spell-learned event. About 0.88 seconds later an outbound event correlated with the existing Papyrus `RemoveItem` trace. This attempt failed the preservation criterion under the active pickup policy; it does not show that the read hook consumed the book. No change to the pickup policy was made in source.

After a reload, the user disabled the mod in the MCM and spawned Firebolt tomes. Multiple inventory uses on the verified thread produced denial rows; the user reported the spell stayed unlearned and the tome remained, with use appearing to do nothing. At 06:52:58 a later reported world READ produced an inbound Firebolt followed by a denial row on worker thread 16472; the subsequent queue drain reported the inbound row and no immediate corresponding outbound. Read Or Take's pickup-before-read means returning false can leave the book in inventory, not at its original world location. Exact counts and the effects of prior spawned copies require separate controlled observation.

The user reported that after the isolated world READ, the tome was taken and could not be used from inventory, consistent with repeated denial. Exact inventory counts and the spell-list state after that particular world interaction were not independently confirmed. World TAKE, unrelated tome and ordinary/skill book controls were not completed during this task. After the marker was removed and the prior forwarding DLL restored, the user reported Firebolt appeared to teach and consume normally; the new 06:59:43 log shows Firebolt inbound, a generic spell-learned notification and Firebolt outbound within milliseconds, with no read probe enabled. This restored-forwarding log and its Papyrus log are preserved in `task08f-preservation`. The notification itself does not identify the spell.

The acceptance criterion remains unmet: the initial active-policy world test removed the tome, and the isolated tests do not establish exact counts or all controls. A generic `spells_learned` notification has no spell ID; menu state and delayed inventory enrichment are not sufficient to prove a particular learning outcome or exact-copy identity. Do not integrate this developer experiment with gameplay until the pickup and read paths have a single coordinated policy and the missing controls are repeated.
