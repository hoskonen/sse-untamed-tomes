# Investigation 06 — Acquisition boundaries

Schema 4 adds synchronous diagnostics to the existing activation and inventory notification sinks. It keeps the bounded inventory queue for later metadata and correlation. These probes are event subscriptions and install no binary hooks on either supported runtime.

Both rows are synchronous with **notification delivery**. They report `phase=notification commit_order=unverified`. This does not establish whether insertion or removal is already visible. The inventory sink copies raw value fields and logs them on the dispatching thread. It does not resolve inventory objects or interrogate UI there. Activation keeps the existing checked-thread requirement, uses the callback-owned reference only within that callback, and can therefore have no row for an activation on another thread. Log output is serialized and flushed and can perturb timings. A zero source or handle means no identifier was supplied. Owner refers to the sampled object, not legal status.

Join `boundary=container_change` to the later `event=container_change` by `session`, `capture_unix_us`, `elapsed_us`, thread, item and count. For activation, use session, target or base FormID and timestamp. With no common instance identifier this is correlation, especially if identical books overlap. Compare capture timestamps against Papyrus removal traces. Deferred menu and location fields remain diagnostic samples, including when the queue drains much later.

## Hook decision

Leave binary hooks disabled. A relocation or matching prologue alone does not establish that a particular caller owns the transaction, that an existing detour is absent, or that a reference can survive cancellation. For world pickup, verify entry and return with a debugger on 1.7.104 before considering a forwarding probe. Use the original handle or a fresh lookup to check the reference after return. A future veto would need a caller that can leave the original book in the world with coherent UI, sound and crime state. For container and barter, look upstream of both transfer legs. Declining a destination insertion after the source decrement can lose an item. Keep book-read detours outside this work. Repeat all address, ABI and conflict checks independently before considering 1.6.1170.

## Runtime checklist

Launch the schema 4 DLL through MO2 on 1.7.104 and keep the same-session native and Papyrus logs. Use a disposable save and leave existing safety settings alone.

1. Activate a placed Firebolt tome, first closing the read view without taking it if offered. Then take it. Compare the activation reference and BOOK `000A26FD` with the inbound row. Check whether each notification precedes or follows other observable steps. Absence of an activation row does not prove there was no activation.
2. Take one tome from a known chest and one from a known corpse. Record both reference IDs and compare them with the raw source on the inbound rows. Take an ordinary non-book item from the same inventory as a control. Where a source is zero, retain that result.
3. Purchase one tome normally. Record the seller, confirmed quantity and price, and compare stock and gold before and after. Repeat with a canceled purchase or non-sale grant while BarterMenu is open. Expect the native classification to remain unknown until an actual purchase outcome is validated.
4. Compare each immediate row with the queued enrichment row and any Papyrus removal. Record missing rows, thread IDs, publication order and queue delay. Do not infer transfer timing from when the queued line was written.

Start classification with **reported container transfer** for an inbound delta with a nonzero source that matches a separately identified chest or corpse reference. Validate that relationship on repeated single Takes and controls before using it as provenance. It does not prove the transfer was lawful, initiated through the menu, or a merchant purchase. Keep world pickup and purchase unknown until their separate boundaries are verified.
