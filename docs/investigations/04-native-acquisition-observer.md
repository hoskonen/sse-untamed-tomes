# Investigation 04 — Native acquisition observer

The SKSE observer supports the Steam Skyrim runtimes 1.6.1170.0 and 1.7.104.0. It reads native events and writes diagnostics. It installs no hooks, changes no inventory or save data, and uses SKSE and Address Library.

## Build and runtime status

- The plugin checkout uses XMake. The vendored dependency also provides CMake for its own build. The tested configuration is Windows x64 `releasedbg` with CommonLib SE and AE enabled and VR disabled. Build with `xmake f -y -m releasedbg --skyrim_se=y --skyrim_ae=y --skyrim_vr=n` followed by `xmake -y`. XMake keeps its output under the C++ checkout and installs the DLL and PDB through CommonLib into the Untamed Tomes MO2 mod.
- MO2's **SKSE** executable is `D:\Steam\steamapps\common\Skyrim Special Edition\skse64_loader.exe`, with the same directory as its working directory. The adjacent `SkyrimSE.exe` file and product versions are both `1.7.104.0`. The loader and `skse64_1_7_104.dll` both report SKSE 2.3.1. The SKSE log's packed runtime `01070680` decodes as major 1, minor 7, revision 104 and low nibble 0. The previous hyphenated display came from the default CommonLib formatter. [SKSE packed versions](https://github.com/ianpatt/skse64/blob/master/skse64_common/skse_version.h)
- The project version was the template's `0.0.0`. XMake now supplies `0.1.0` to both the Windows DLL resource and CommonLib's exported SKSE declaration. Logs use dotted four-component values from the export and the running runtime, such as `plugin_version=0.1.0.0`.
- The previous CommonLib revision classified minor 7 as SE and lacked the format-5 Address Library reader. The submodule now pins CommonLibSSE-NG v16.4.0 (`9955ae3b18dd0aedbebb58fa207a4b7180eb6d67`), which treats 1.7 as AE and supports both formats. [CommonLib v16.4.0](https://github.com/alandtse/CommonLibSSE-NG/releases/tag/v16.4.0)

| Machine | Executable | SKSE | Address Library |
| --- | --- | --- | --- |
| Development | Steam 1.7.104.0, independently verified | 2.3.1 installed | `versionlib-1-7-104-0.bin`, format 5 |
| Main | Steam 1.6.1170.0, verify on that machine | Matching Steam build, such as 2.2.6 | `versionlib-1-6-1170-0.bin`, format 2 |

The runtime guard uses CommonLib constants for these two executables. SKSE's decoded version must agree with CommonLib's executable metadata, and the relevant Address Library file must be readable with the matching header. Other runtimes and failed preflight checks leave the observer inactive with a diagnostic if SKSE invokes the plugin. For failures during SKSE's own compatibility checks, consult `skse64.log`. CommonLib performs the actual address resolution. The two local Address Library files have nonzero offsets for all 19 observer-related IDs checked offline. This does not establish calling semantics or layouts. The SKSE declaration marks the plugin as structure-dependent and declares the post-1.6.629 structure ABI, which SKSE 2.2.6 requires for an Address Library plugin that uses gameplay structures. [SKSE 2.2.6 compatibility checks](https://github.com/ianpatt/skse64/blob/v2.2.6/skse64/PluginManager.cpp#L516)

Formatting, timestamps and classification use ordinary C++ and have no Skyrim ABI dependency. Registering the two sinks and reading engine data require CommonLib's relocated event source singleton, main-thread record, form/handle lookup, player, UI and menu globals, and reference accessors. They also depend on CommonLib's event, reference, book and menu layouts. The same observer code is used on both versions. Future hooks need separate verification of their caller, target, calling convention and relocation on each version.

## Event flow and log fields

### Schema 3 input-boundary drain

The second 1.7.104 capture recorded initial task thread 22912, then drain threads 22568, 12928, 4412 and 7664 with 5–34 ms of queue latency. The window owner and `RE::Main::threadID` both stayed at 22912. CommonLib forwards `AddTask` to SKSE, which runs queued work at two engine task-pool call sites. The initial main-thread sample describes that invocation only. `AddUITask` has a separate UI command pump, but its thread and suitability for world-reference reads would require their own verification. [SKSE task pool](https://github.com/ianpatt/skse64/blob/master/skse64/Hooks_Threads.cpp) · [SKSE UI queue](https://github.com/ianpatt/skse64/blob/master/skse64/Hooks_UI.cpp)

At `kInputLoaded` the observer registers a read-only input event sink. The sink checks the current thread against both the process-owned Skyrim window and the engine main-thread ID before draining up to 64 entries per callback. A failed check leaves pending events in FIFO order for a later eligible callback. Overflow still drops new events at 512 entries and reports the count on a successful drain. Input dispatch can pause or be absent, so resolution can lag until input resumes and load transitions still discard pending observations. Menu state and reference lifetimes reflect the drain time. The capture time, FormIDs and raw handle remain in the row even if a lookup fails.

The queued scalar copies can be processed on any thread. CommonLib's form lookup takes a read lock on the form map, then returns a raw pointer after releasing the lock. A BOOK teaching flag and its link generally describe loaded record data, but this lookup alone supplies no lifetime or immutability guarantee for the returned objects, especially during session transitions. The observer therefore reads even book metadata on the checked input boundary and keeps handle resolution, cell, ownership and UI reads there too.

### Reference implementation at v1.2.2

- `Patches.cpp` validates an instruction pattern and installs distinct flat/VR code patches inside `TESObjectBOOK::ProcessBook`. The replacement invokes the callback with the book and spell from the live reading path, skips the vanilla spell-learning and tome-consumption block, and resumes later in the original routine. Its execution context comes from that caller. [Patches.cpp](https://github.com/Exit-9B/Dont-Eat-Spell-Tomes/blob/v1.2.2/src/Patches.cpp)
- `SpellTomeManager.cpp` queries the active ContainerMenu's Scaleform movie for whether the player is viewing container items. Only in that case does it resolve the menu's target reference handle for the optional container argument. This describes the reading UI at the moment of the call. It does not establish where an inventory item came from. [SpellTomeManager.cpp](https://github.com/Exit-9B/Dont-Eat-Spell-Tomes/blob/v1.2.2/src/SpellTomeManager.cpp)
- `Registration.cpp` names the singleton registration set `OnSpellTomeRead`. The manager queues book, spell and optional container to registered Papyrus recipients after the synchronous context lookup. The companion serialization code saves and reloads registrations. This is a Papyrus delivery mechanism with no proof of main-thread affinity for general SKSE tasks. The transferable idea is to take context at a known engine boundary and keep delayed delivery separate. Our observer keeps scalar data from the acquisition notification and uses a checked input callback. [Registration.cpp](https://github.com/Exit-9B/Dont-Eat-Spell-Tomes/blob/v1.2.2/src/Registration.cpp) · [Serialization.cpp](https://github.com/Exit-9B/Dont-Eat-Spell-Tomes/blob/v1.2.2/src/Serialization.cpp)

### Schema 2 baseline

The 1.7.104 baseline delivered inventory callbacks on thread IDs 22104, 7128, 23744 and 13216. A new launch verified SKSE's task callback on thread 2836, which matched both the Windows owner of the Skyrim window and CommonLib's `RE::Main::threadID` in that process. Thread IDs are process-local. The baseline had no same-process main-thread ID sample, so its four callback IDs establish multi-threaded dispatch. They do not establish which of those four was the main thread.

The inventory sink copies IDs, count, the non-owning reference handle, unique ID, capture time and thread into a 512-entry FIFO. Queue admission assigns sequence numbers under a mutex and schedules one SKSE drain. The FIFO drops new events when full and reports the count, with corresponding sequence gaps. Save/load markers discard pending work and advance the session. [SKSE task dispatch](https://github.com/ianpatt/skse64/blob/master/skse64/Hooks_Threads.cpp)

The drain verifies its thread against the process-owned Skyrim window before resolving forms, handles, owners, source and destination, or reading UI and location. Resolution uses current objects and can fail when a reference has disappeared. A resolved item handle must still refer to a live reference with the expected base form. `context=deferred` labels samples taken during the drain. `queue_us` reports the capture-to-resolution delay and `capture_unix_us` gives the wall-clock capture time for matching Papyrus logs. The activation sink uses the verified thread ID and otherwise skips the activation. Source or destination ID zero indicates the event supplied no endpoint to resolve. Outbound rows are inventory removals and carry `direction=outbound`. Acquisition remains unknown.

The old run shows one inbound and one outbound event for each of `000A26FD`, `000A2705`, `000A26F9` and `00109112`, with 1.03–1.67 seconds between each pair. Matching Papyrus FormIDs, counts and `RemoveItem` trace times support attributing the outbound legs to the existing monitor. The schema 2 build reached `observer_ready` and verified its drain thread on 1.7.104. It still needs a repeat acquisition run to confirm the resolved rows for all four tomes and a smoke test on 1.6.1170. The standalone C++ queue test covers FIFO order, wraparound, overflow reporting, scheduling and two concurrent producers.

1. SKSE calls the plugin load export. The plugin opens `UntamedTomesSKSE.log` under the Skyrim user-data `SKSE` folder and logs its version and the runtime. After preflight it logs `runtime_verified` and registers a messaging listener. At `kDataLoaded` it subscribes to `TESContainerChangedEvent` and `TESActivateEvent` and writes `observer_ready`.
2. For any container change with the player as either endpoint, record the raw source, destination, base item, signed count, reference handle and unique ID. Include outgoing changes so gold, sales, and any subsequent Papyrus removal can be inspected. Gold is base FormID `0000000F`.
3. On the engine main thread, resolve book metadata, the event handle where possible, and the source reference. Sample owner and cell IDs and the current player cell and location. Record open states for barter, container, inventory, book and console, along with pause state and the applicable menu target handles and container mode. Owner fields describe the sampled reference, cell is a separate field, and stack ownership is unavailable. Zero denotes absent or unresolved IDs. `source_resolved` distinguishes an unresolved source from a resolved reference with no reported owner.
4. For player activation of a book, container or NPC on the main thread, record the reference, base form, owner, cell and location. Activation and inventory change are independent notifications. A matching pair supports correlation, and either event can occur without the other.
5. The sinks always return `kContinue`. The container event carries no effective transfer reason or veto. Its dispatch time relative to inventory insertion, activation, crime handling, UI feedback and Papyrus scheduling remains a runtime question.

Rows use key-value fields with a wall-clock log prefix, monotonic callback-entry `elapsed_us`, process-local inventory sequence and callback thread ID. The plugin truncates its log on each launch. The file sink serializes writes and flushes each row. Flushes can affect timing during bursts. With an unverified drain thread the plugin retains the raw payload and uses `context=unavailable`, `item_kind=unresolved`, and menu value `-1`. Inventory rows follow FIFO admission order. Activation and session markers are separate observations and can interleave.

The teaching flag and linked spell are logged separately. A conventional vanilla or mod-added `TESObjectBOOK` with a teaching flag and resolved spell logs `item_kind=spell_book`. A flagged book with no linked spell logs `missing_spell`, and an ordinary or skill book logs `other_book`. A scripted spell grant without a teaching link has no native tome metadata. These outcomes follow the linked CommonLib book accessor and still need fixture coverage in game. [CommonLib book implementation](https://github.com/alandtse/CommonLibSSE-NG/blob/b9f1e9b4e4b102f95bb63590b0b31542c5d49747/src/RE/T/TESObjectBOOK.cpp)

## Acquisition evidence and runtime checklist

Run the same DLL in each MO2 profile with the corresponding SKSE and Address Library. Require `observer_load` with the expected dotted runtime, `runtime_verified` with the expected format, `observer_ready`, and a successful save load. Pick up a tome and verify its `container_change` row before starting the matrix. Use a disposable test save. First run a vanilla acquisition control with Untamed Tomes gameplay disabled via its existing MCM. For Papyrus comparison, enable gameplay and debug logging with the instrumented PEX winning in MO2 and `bEnableLogging=1` / `bEnableTrace=1` under `[Papyrus]`. Keep the trace and native log from the same launch.

### Preliminary model

Treat the provenance of a change as unknown until evidence identifies a committed action. Keep mechanism and theft evidence separately so world pickup and container transfer can both carry theft attribution. Location and menus describe context. Source/destination can reliably describe the endpoints reported by a transfer event. A resolved teaching link identifies book metadata. The payload alone cannot reliably identify the initiating action.

| Classification | Evidence needed |
| --- | --- |
| Verified merchant purchase | A matched committed sell-to-player operation, or a runtime-validated purchase-outcome signal tied to the item, seller and quantity with failed transactions excluded. Barter openness, target and adjacent gold rows are corroboration only. |
| World pickup | A validated physical pickup path tied to the original reference. A matching book activation with a source-less delta is a candidate. A zero source can also occur on grants. |
| Container transfer | A matched successful transfer from the source. A nonzero old container can describe reported origin without establishing manual looting, Take All or a sale. |
| Theft | A theft-specific signal tied to the acquired item and source. Ownership mismatch, steal mode and crime deltas strengthen the case. Legality can depend on faction membership or permissions, and undetected theft can leave the bounty unchanged. |
| Scripted addition | A known script or console invocation correlated with the resulting change. Missing source and reference fields alone are ambiguous. |
| Unknown | Use when the evidence is missing, conflicting, or cannot be matched to the specific action. The observer emits this for every container row. |

CommonLib models an independent Story Manager payload, `BGSAddToPlayerInventoryEvent`, with `kBuy`, `kPickup`, `kContainer`, `kSteal`, `kPickPocket` and `kDeadBody`. The pinned headers expose an event index and a Story Manager producer interface. There is no ordinary observer subscription for that payload through `ScriptEventSourceHolder`. It lacks quantity and a transaction ID. Inspect the 1.6.1170 producer to establish which branch emits Buy, whether it follows success and how it identifies the merchant. Compare cancel, failed purchase, batch purchase, sale and unrelated while-open transfer before using it. If it cannot be correlated reliably, trace the accepted BarterMenu transaction branch and its item and payment legs. Classification supplies evidence to a later magic policy and grants no protection by itself. ## First interception experiment

The CommonLib actor wrapper dispatches `PickUpObject(TESObjectREFR*, int32_t, bool, bool)` through flat vtable slot `0xCC`. The book form also overrides `Activate`. Neither declaration establishes that ordinary activation reaches that slot, that the reference survives return, or where the sound and UI are committed.

Use read-only debugger breakpoints first in the exact 1.6.1170 executable. Resolve the player vtable with the matching Address Library and independently verify slot `0xCC`, its target and the caller in disassembly. Confirm the Windows x64 argument mapping and distinguish activation, BookMenu Take and direct pickup. At entry capture FormID, handle, count and sound flag. At return check the handle afresh without dereferencing the prior raw pointer. Compare the native rows with inventory insertion, HUD and pickup sound call sites and the video capture.

If a later forwarding diagnostic is needed, scope it to a verified player call site, forward the original exactly once and preserve all inputs and return semantics. Patch conflicts, thread affinity, and reference invalidation make an unverified hook risky even when it forwards. Consider cancellation or redirection only after finding a pre-commit branch whose caller can handle an intact reference and consistent feedback, inventory and crime state. No interception was installed in this build. [Actor wrapper](https://github.com/alandtse/CommonLibSSE-NG/blob/b9f1e9b4e4b102f95bb63590b0b31542c5d49747/src/RE/A/Actor.cpp)
