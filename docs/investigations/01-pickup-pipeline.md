# Investigation 01 — Tome Pickup Pipeline and SKSE Feasibility

## Findings

Runtime observations supplied for this investigation confirm that the SkyUI MCM works, base Magicka affects rejection, town pickups are safe, and dungeon pickups can reject. A rejected tome eventually disappeared after roughly five seconds, with unwanted audio during the interaction. The delay was observed at the UI. Neither the point at which inventory changed nor the source of the sound was measured.

Start with the instrumented Papyrus run. The current script has avoidable work and debug UI activity. A source audit cannot establish whether either accounts for five seconds. Native code is promising if the dominant delay precedes Papyrus entry, or if rejected pickups must avoid insertion and its associated feedback. CommonLibSSE-NG exposes useful observation and hook candidates, with transaction behavior still to verify on 1.6.1170.

## Original Papyrus event flow

1. The player reference alias receives `OnItemAdded` after an addition. It checks the enable global, base form and bound `MagicTomeKeyword`, then tests that keyword on the base form. There is no filter registration in this script. The actual event volume should be checked on the active alias/profile.
2. With debug enabled, it resolves the player and current location, classifies the location and posts a context notification and trace. It separately polls `BarterMenu`, calls the safety predicate and posts another notification and trace. The predicate polls barter first and otherwise resolves the player and location again, checking Dungeon before City/Town, Inn and Store.
3. The first gameplay safety gate calls that predicate again. A safe return can perform another location lookup to format the debug log. The custom safe keyword comes next, then the second gameplay safety gate. An unsafe tome passing both gates with debug on can cause four barter polls and four location classifications when all polls say barter is closed. With debug off there are two gameplay polls and two classifications on that path.
4. It checks the exclusion FormList and, if an item reference exists, calls Papyrus Extender's `IsQuestItem`. The vendor-chest branch is commented out. The source container plays no part in purchase attribution. An open barter menu at handler time exempts the event regardless of source.
5. It resolves the player again, falling back to `Game.GetPlayer()`. On first eligible-for-evaluation pickup it captures level and six base magic skill values, then immediately reads level and those six values again for the progression classifier. Subsequent pickups still run the classifier with debug off. Its return value is unused for rejection. The script then reads the threshold global (default zero), reads base Magicka, and with debug enabled formats, traces and posts the values. At or above threshold it returns.
6. Below threshold it queries the current count for the base form. If positive, it calls `RemoveItem(baseForm, 1, true)` without a destination. It then posts the rejection notification and calls the trace-plus-notification logger in debug mode. The removed copy is selected by base form. The event count and the instance reference do not drive the removal.

The installed Creation Kit declarations expose `OnItemAdded` on `ReferenceAlias`, and declare `RemoveItem` as a void native function. There is no explicit wait, update timer, polling loop or message box in this handler. Native declarations alone do not describe VM scheduling or when an engine mutation becomes visible. The SKSE menu query delegates to the menu manager. It contains no explicit menu-close wait. [SKSE Papyrus UI implementation](https://github.com/ianpatt/skse64/blob/v2.2.6/skse64/PapyrusUI.cpp)

| Interval | What could account for it | Evidence |
| --- | --- | --- |
| Input to Papyrus entry | Acquisition itself, paused menu behavior, queued inventory events, VM budget and other scripts. Take All can deliver many events close together. | Plausible. No input or native timestamp exists in the script. |
| Entry to removal call | Repeated context and debug work, progression reads, VM scheduling between calls, quest item lookup, count query. | Code confirms the calls. Their costs and any pauses require measurement. |
| Across the removal call | Native work and time before Papyrus resumes after the call. | Bracketed by the new samples. The duration alone cannot attribute time to engine execution. |
| Return to visible inventory update | Menu refresh, queueing or observing the change only after reopening a menu. | Plausible. The call returns no success or refresh status. |

Removal can produce a player `OnItemRemoved` and engine inventory/UI events. This alias has no removal handler. With no destination, its own removal is not a direct player addition. Other mods may react by transferring or restoring items, and overlapping additions can race with each other or player actions between count and removal. A late callback can remove a pre-existing copy after the newly acquired copy was consumed or transferred. Check for duplicate or interleaved events during bursts. The two context gates can also disagree if a menu or location changes mid-handler.

## Instrumented build

Use the existing **Debug logging** MCM toggle. In the test profile's Skyrim.ini, set `bEnableLogging=1` and `bEnableTrace=1` under `[Papyrus]`, then read `Papyrus.0.log` under the Skyrim user-data directory's `Logs\Script`. Filter for `[UntamedTomes][Pickup`. The existing progression trace uses a separate prefix.

Each tome trace carries a near-entry timestamp captured after the debug-toggle read and before the enable and keyword gates. The first row records identification, addition count, item reference and source. Gate rows record the actual context results, and decision rows identify exemption, abort or threshold outcome. Menu mode and InventoryMenu, ContainerMenu and BarterMenu openness are sampled after identification and around removal. These are sequential snapshots and can change between samples. The earlier removal sample is taken immediately before the call, after capturing menu state. The later sample is taken as soon as the script resumes, and both are printed after the call to keep trace output outside that bracket. A missing pair can also mean the call never returned or the trace was lost.

The clock is `Utility.GetCurrentRealTime()`, an application-relative float in seconds. The installed Utility declaration describes it as the same clock used by `WaitMenuMode`. It can advance during menus, with gaps possible when the engine is frozen. Confirm behavior in the test profile against a recording. Float spacing grows with uptime (about 0.24 ms at one hour and 3.9 ms at ten hours for a 32-bit float). Engine update cadence and Papyrus log formatting can make effective resolution coarser. A zero delta means the samples were indistinguishable at this precision. Compare multi-frame or multi-second intervals, and measure elapsed time from the provided deltas. The near-entry sample excludes the input, native event delivery and VM queue interval before the script starts. Form and entry time are correlation hints that can collide during a burst.

Diagnostics use the debug flag sampled at entry. Rejected pickups still remove one copy by base form with the silent flag, using the same exemptions and threshold. The two gameplay context gates and saved progression behavior are retained. Debug notifications and the extra debug context evaluations were removed to isolate the mod's own UI output and reduce measurement overhead. Trace formatting, menu queries, VM scheduling and log output still perturb the debug run. With debug off the pickup timing and menu probes are skipped.

## Papyrus options

- **Filter by registered forms.** The installed `ReferenceAlias.psc` describes exact-form and FormList matching. Passing a Keyword form does not express `HasKeyword` on the added item. There is no built-in predicate filter for all spell tomes. The existing keyword test recognizes conventionally tagged mod-added tomes without list maintenance, while still receiving unrelated additions. A generated list is feasible with the existing Papyrus Extender dependency. Enumerate loaded book forms by keyword using `GetAllForms` and register those forms or build a FormList. Measure setup and save/load cost and test refresh when the load order or tags change. A keyword query still misses untagged spell-teaching books. A generated list based on spell metadata could include those, which would expand current behavior. Dynamic forms and runtime tag changes need explicit coverage. For this investigation, keep the current predicate. [Papyrus Extender source declarations](https://github.com/powerof3/PapyrusExtenderSSE/blob/master/Papyrus/Source/scripts/PO3_SKSEFunctions.psc)
- **Reduce work once measured.** Evaluate context once per pickup and reuse player and location within that decision if the timing tests support a single snapshot. Gate progression observation where possible while preserving first-observation baseline semantics for old saves. Keep the keyword check early and avoid debug string building when tracing is off. Optimize the largest measured interval first.
- **Keep immediate post-event removal as the baseline.** Deferring until menu close can reduce visible row churn if it is the source of feedback, but extends the window in which the tome can be read, sold or transferred. It also risks stale context and instance identity and needs a separate queue across menu and save/load boundaries. Inventory and container menus may pause the world, affect VM scheduling, or refresh separately from the actual mutation. Compare held-open and quickly closed menus before considering deferral.
- **Isolate sound by source.** The original `Debug.Notification` calls are verified UI activity. The code contains no explicit sound play call, and the reported sound has not been attributed to notifications. `abSilent=true` is a flag on the removal call. The initial pickup can already have played its item sound, produced a HUD message, or triggered a menu response. List movement and menu click/confirmation sounds are separate candidates. Avoid global sound or Scaleform patches while isolating these signals. Compare audio at input, at notification display and at inventory row change using baseline, debug-off and trace-only runs.

**Intercept or redirect.** CommonLib wrappers give access to engine calls. A veto requires a verified pre-commit hook at a path where its caller can handle cancellation. Redirecting after an addition is a second mutation, with its own events and possible feedback. Skipping a lower-level addition does not have the semantics of cancelling an activation, a transfer or a sale. Verify each caller before considering a behavior-changing prototype.

**Suppress feedback.** The world pickup sound parameter and `Actor::PlayPickUpSound` are audio candidates. The book form has a pickup/putdown sounds component. Log-only probes should identify actual callers and ordering. HUD notices, menu click/confirmation cues, row refresh and crime feedback may occur on independent paths. Only consider transaction-scoped suppression after finding the offending call. Muting by base form globally can also mute legitimate pickups of the same tome. ## Hybrid design and compatibility

A native observer can capture source, destination, count, menu and timing and queue Papyrus notifications for asynchronous policy or effects. For a synchronous pre-insertion decision, native code must already have the necessary policy and settings. A Papyrus callback through the VM would reintroduce scheduling and blocking hazards. Keep MCM writing the current globals, and read a coherent settings snapshot on a verified safe engine thread. Preserve current safe-context precedence and quest exemptions. Papyrus can still own slower progression logic and optional effects using ESP-provided spells and visuals. A future native mutation path needs one owner of removal so both handlers cannot reject the same acquisition.

Capture thread ID and ordering first. Assume callback thread affinity and lock state are unknown until verified. The library's event dispatch holds a lock while notifying sinks. Avoid inventory mutations, VM waits and Scaleform calls inside a sink. Copy identifiers or safe handles into a bounded queue, re-resolve them on the appropriate engine thread, and invalidate pending work on save/load transitions. Avoid keeping raw inventory entry or extra-list pointers across callbacks. A delayed action must revalidate the item, ownership and settings. Do not let a callback's own mutation start a second rejection loop.

Test with SkyUI and vanilla menu variants, pause-changing mods, scripted looting or grants, quest aliases, and other DLLs that hook the same paths. Runtime-specific relocations and correct ABIs are necessary, including validation of any vtable or call-site hook. An Address Library match alone says nothing about the transaction phase. Menus may be replaced or run unpaused. [Skyrim Souls RE hook and menu compatibility notes](https://github.com/Vermunds/SkyrimSoulsRE)

1. In an isolated MO2 profile, verify the winning PEX and matching runtime dependencies. Capture synchronized screen and game audio. 3. Repeat for a single container take and Take All with the menu held open several seconds and closed immediately. Include a barter purchase with quick menu close, an unrelated scripted addition during barter, an owned world pickup, a stolen container take and pickpocket if applicable. Check a mod-added tagged tome, an untagged spell-teaching book, a regular book, an excluded or quest tome, a multi-count stack and a pre-existing copy with different ownership. Try a busy VM profile and a quiet one. Record actual removed counts and whether each sound survives the disabled-mod and debug-off runs.
4. If the entry-to-call interval dominates, optimize the expensive measured Papyrus stage and repeat. If the visible delay occurs mostly before the first sample or after the call bracket, use an observational 1.6.1170 native prototype next. Log a monotonic high-resolution clock (such as QPC), thread, input/operation boundaries, container events, sound/UI requests and an explicitly correlated Papyrus entry sample. Use an instrumented native timestamp callable at Papyrus entry or calibrate both clocks and report the overhead. Compare matched trials and avoid inferring dispatch time from two unrelated clock epochs.
5. Consider a world-pickup-only interception prototype if the verified source of unwanted feedback is insertion or an earlier pickup cue, or if faster post-event rejection still permits unwanted use. Expand to transfer paths only after their transaction ordering and ownership behavior are verified. If the dominant issue is retained solely in menu refresh or UI audio, test that specific path before adding transaction interception.
